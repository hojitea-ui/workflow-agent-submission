# 결정 기록

카드뉴스 에이전트(`card-news-workflow-kit`)의 D1~D21에서 이어 쓰는 것과, 이번에 새로 정한 것을 나눠 적는다. "사용자"는 사용자가 직접 답한 것, "AI"는 합리적인 기본안으로 정하고 기록한 것이다.

## 이번에 새로 정한 것
| # | 결정 | 정한 사람 | 이유 |
|---|---|---|---|
| R1 | 새 폴더 `report-review-kit`로 복사해서 만든다. 카드뉴스 폴더는 그대로 둔다 | 사용자 | 카드뉴스 제출 결과(ACCEPTANCE, 내보낸 파일)가 망가지지 않고 두 프로젝트가 섞이지 않는다. |
| R2 | 입력은 제목·조건을 적고 글을 붙여넣거나 .md/.txt 파일을 올린다. Word(.docx)는 받지 않는다 | 사용자 | 추가 설치가 없고 문단 번호를 정확히 매겨 지적을 정확하게 한다. |

| R4 | 기능은 가장 작게: 한 번의 검수→선택→수정→재검수 흐름만 | 사용자 | 요청("기능은 가장 작게 해 줘"). |
| R5 | 지적은 최대 5개, 방향은 지적마다 2개와 추천 1개 | AI | 선택해야 할 양을 줄이고 화면을 단순하게 한다. |
| R6 | 글은 빈 줄로 나눈 문단(P1, P2…)이 단위다. 수정도 문단 전체를 한 번에 바꾼다 | AI | 문장 단위 편집은 복잡하다. 문단 단위면 바뀐 곳과 안 바뀐 곳을 기계로 검사할 수 있다. |
| R7 | 지적의 인용문은 그 문단에 실제로 있는 문장이어야 한다. 없으면 한 번 고쳐 쓰게 하고 그래도 없으면 인용 없이 문단만 가리킨다 | AI | 모델이 있지도 않은 문장을 지적하는 일을 막는다. |
| R8 | 자료가 부족하면 문단을 고치지 않고 `⚠[자료 보강 필요: …]`를 덧붙인다. 완료로 세지 않는다 | AI | 근거를 지어내지 않고 부족한 부분을 눈에 띄게 한다. |
| R9 | 수정에 쓴 근거 주소는 이번 검색·열람 기록에 있는 것만 인정한다. 본문 속 `[n]`은 참고 자료 목록과 짝이 맞아야 한다 | AI | 카드뉴스에서 쓴 방식을 그대로 가져온다(지어낸 링크 방지). |
| R10 | 재검수는 (1) 기계 검사: 고르지 않은 문단이 그대로인지, 인용 표시와 자료 목록이 맞는지, 새 수치가 근거에 있는지 (2) Claude 판단: 처음 지적이 해결/일부/미해결인지 | AI | 기계로 확인되는 것은 기계로 확인하고, 해결 여부 같은 판단만 모델에 맡긴다. |
| R11 | 포트 기본값은 8770이다(8765는 카드뉴스 앱이 쓴다). 충돌하면 다음 번호 | AI | 두 앱을 같이 켜도 부딪히지 않게 한다. |

## 카드뉴스에서 그대로 이어 쓰는 것
- Python + FastAPI + uvicorn, SQLite(`data/app.db`), 화면은 서버 상태를 폴링하는 바닐라 JS (D1~D5).
- 엔진은 Claude CLI, 모델 sonnet, effort medium, 도구는 WebSearch·WebFetch만(`--restricted`), 프롬프트는 표준입력, 결과는 JSON 규격(`--json-schema`) (D9).
- 127.0.0.1에만 바인딩. 서버가 강제로 꺼져도 하위 프로세스가 같이 끝나도록 Windows Job Object 사용.
- 실패는 완료로 처리하지 않고 원인과 다시 시도를 보여 준다. 작업 취소는 하위 프로세스까지 종료한다.

## 사용해 보고 추가로 정한 것 (2026-10-24)
| # | 결정 | 정한 사람 | 이유 |
|---|---|---|---|
| R12 | **"가장 작게"의 기준**: 입력·출력 형식(docx, PDF)이나 계정처럼 범위를 넓히는 것은 뺀다. 검수→선택→수정→재검수→산출물의 고리를 쓸 수 있게 하는 데 꼭 필요한 것(고치기 전·후 변경 표시, 고친 내용 복사, 잘리지 않는 글, 실패 안내)은 작은 범위에 포함한다 | 사용자+AI | 검수 결과는 "무엇이 바뀌었는지"와 "바뀐 글"이므로 그것을 볼 수 없거나 가져갈 수 없으면 워크플로가 끝나지 않는다. |
| R13 | 변경 표시는 단어 단위 비교로 삭제 ~~취소선~~, 추가 **굵게**(마크다운 리포트)와 `<del>`/`<ins>`(화면). 같은 글이 긴 구간은 줄이고, 고치기 전·후 전문은 접어 둔다 | AI | 긴 문단에서 바뀐 곳이 묻히지 않게 한다. |
| R14 | 글자 수 제한은 글을 중간에서 뚝 자르지 않는다. 문장 끝(없으면 띄어쓰기)에서 `…`로 줄이고, 프롬프트에서 간결하게 쓰게 한다. 인용문(quote)만은 원문 일부여야 하므로 `…`를 붙이지 않는다 | 사용자 지적+AI | 자료 부족 설명이 `…인용해야 한`에서 잘리는 문제가 있었다. |
| R15 | **재검수는 근거를 보고 판단한다**: 쓴 출처(번호·제목·주소·인용)와 앱의 기계 검사 결과를 같이 주고, 새 문제는 "이번 수정이 만든 것만, 중요도(높음/보통/낮음)와 함께 최대 2개"로 제한한다. 출처 목록에 있는 `[n]`을 "출처 없음"이라 하는 것은 문제로 치지 않는다 | 사용자 지적+AI | "새로 생긴 문제"가 잡음(출처 오탐 등)이 많고 중요도가 없어 쓸 수 없었다. |
| R16 | **라운드(B)**: 중요도 높음·보통인 새 문제는 수정 방향 2개를 달아 두고, 사용자가 "이 문제도 고치기"로 고르면 고친 글에서 이어서 다음 라운드(최대 3번)를 돈다. 낮음은 접어서 참고로만 보여 준다. 참고 자료 번호는 라운드를 넘어 이어 붙인다 | 사용자 | 새 문제를 보고도 할 수 있는 일이 없던 막다른 길을 잇는다. |
| R17 | "쓸 만한 상태"는 중요도 높은 새 문제, 미해결, 자료 부족이 모두 0일 때만 표시한다. 보통·낮은 새 문제와 일부 해결은 남아 있어도 되지만 리포트의 "남은 문제"에 적는다 | AI | 자료 부족 표시(`⚠`)가 남은 글을 완성으로 보이게 하지 않는다. 최종 판단은 사용자가 한다. |
| R18 | 분석 때의 문단을 저장해 두고 라운드마다 그 글로 이어 간다 | AI | 나중에 문단 나누는 규칙이 바뀌어도 지적의 문단 번호가 어긋나지 않는다. |
| R19 | 같은 문단에 지적을 둘 이상 골라도 지금은 차례로 고친다(한 번에 묶어 고치기는 하지 않는다) | 사용자+AI | 범위를 작게 유지한다. 대신 재검수가 각 수정 직후의 글을 기준으로 판단한다. |

## 근거 없는 내용은 만들지 않기 (2026-10-24, 사용자 지시)
| # | 결정 | 정한 사람 | 이유 |
|---|---|---|---|
| R20 | 근거를 확인할 수 없는 수치·연구·인용은 모델이 추측하거나 채워 넣지 않는다. 프롬프트에서 금지하고, 검색한 자료 또는 사용자가 제공한 자료에서 확인한 것만 새로 쓰게 한다 | 사용자 | 지어낸 근거는 검수 도구가 가장 피해야 할 실패다. |
| R21 | 수정 결과에 **보류(held)**를 둔다: `claim`(확인하지 못해 쓰지 않은 내용)과 `needed`(필요한 추가 자료: 어떤 문헌·통계인지 구체적으로). 근거가 일부만 있으면 그 부분만 고치고 나머지는 보류, 하나도 없으면 문단을 그대로 두고 전부 보류(`insufficient`) | 사용자+AI | "확인된 것과 확인되지 않은 것을 구분하고 부족한 근거와 필요한 자료를 명시"하라는 요구를 데이터로 남기기 위해서다. |
| R22 | 글 안에는 짧은 표시 `⚠[자료 보강 필요: 내용 (필요한 자료: …)]`만 남기고(내용 80자·자료 100자 안팎), 전체는 화면과 리포트의 "보류한 내용 / 필요한 추가 자료"에 적는다 | AI | 긴 설명이 본문을 뒤덮지 않게 한다. |
| R23 | **사용자에게 추가 자료를 요청**한다: 보류 항목 아래에 붙여 넣는 칸을 두고, 붙여 넣으면 그 항목이 다음 라운드의 지적(방향: 제공한 자료로 보강 / 제공한 자료 + 웹 검색)이 된다. 붙여 넣은 자료는 데이터로만 취급하고 출처는 "사용자 제공 자료"로 번호를 붙인다. 인용문이 붙여 넣은 자료에 그대로 없으면 "확인 필요"로 알린다 | 사용자 | 앱이 못 찾은 자료(책 원문, 수업 자료 등)를 사용자가 직접 줄 수 있게 한다. 지어낸 인용을 기계로 걸러 낸다. |
| R24 | 자료를 받아 다시 고칠 때 그 문단의 이전 ⚠ 표시는 지우고, 그 자료로도 확인하지 못한 것은 모델이 보류로 다시 적게 한다. "쓸 만한 상태"는 보류한 내용이 0일 때만 표시한다 | AI | 해결한 보류 표시가 남거나, 풀리지 않은 보류가 사라지는 것을 막는다. |
| R25 | 글쓴이만 아는 내용(직접 겪은 일·감정·개인적 이유·의도)은 글에 없으면 모델이 새로 쓰지 않는다. 수정 방향 설명의 "예:"는 보기일 뿐 글쓴이의 말이 아니다. `held.needed`에는 필요한 추가 자료만 쓴다(처리 설명 금지) | AI | 아주 짧은 글(두 문장)을 실제로 돌렸더니 방향 설명의 보기를 글쓴이의 이유로 써 넣었다(VALIDATION.md "STEP 13-3"). 사실을 지어내지 않는 R20을 글쓴이 본인의 이야기까지 넓힌 것. 프롬프트만 바꿨고 효과는 한 번 다시 돌려 확인했다. |
